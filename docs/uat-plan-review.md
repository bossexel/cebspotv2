# CEBSPOT UAT plan review

Reviewed: October 6, 2026 (Asia/Manila).

Follow-up: the [October 13 audit-to-UAT alignment](uat-audit-alignment-2026-10-13.md) maps all 20 scenarios to current engineering evidence, identifies local fixes and required retests, and traces all ten launch blockers. It supplements this plan review; it does not supply participant PASS/FAIL results.

Source: the user-supplied “CEBSPOT User Acceptance Testing (UAT) Plan.” Compared with the current workspace source, including uncommitted changes. This is a document and implementation review, not an executed UAT cycle. No participant results, device results, or deployment status are inferred from source code. Earlier release/manuscript reviews were used as context; current source takes precedence.

**Assessment: the plan has a useful structure and covers the main roles, but needs revision before execution and sign-off.** It includes preparation, two cycles, defect tracking, evaluation, traceability, and acceptance. The main problems are inconsistent sample counts, test steps that do not match the app, and acceptance rules that permit unresolved serious issues too easily.

## 1. Corrections required before testing

| Finding | Required correction |
| --- | --- |
| Header and participant table specify 20 Spotters, 1 owner, and 2 admins, but the total is 27; owner IDs run SO-01 to SO-05; the evaluation table says owners (5). | If the approved sample is 20 + 1 + 2, use **23 total**, **SO-01**, and **Spot Owners (1)** throughout. If it is 20 + 5 + 2, change the owner count to 5 throughout. Do not change the approved research sample just to resolve arithmetic. |
| Platform describes Android only, but the app also contains an admin console and a web owner portal. | Identify which interface each role will actually test. Record browser/version if web portals are used, and Android model/version for native tests. The README identifies `/admin` as the admin console. |
| Build/version and UAT period are blank. | Before Day 5, record app version, installed build identifier, source revision or snapshot, backend/schema version, payment mode, devices, and exact dates. A later build requires an identified retest cycle. |
| “Critical or High issues are fixed or written down with a reason” allows serious defects to remain open. | Require no unresolved Critical issues and no unresolved High issues affecting core tasks, authorization, privacy, booking consistency, or payment integrity. Any permitted exception needs an explicit decision, approver, affected requirement, and limitation. “Accepted with Minor Issues” should refer to agreed Medium/Low issues. |
| NOT TESTED means both unexecuted and outside scope. | Add **NOT APPLICABLE (N/A)** for formally excluded requirements, with a reason and approval. Keep NOT TESTED for applicable cases that were not executed. An absent required feature is a scope gap, not automatically N/A. |
| Several assertions are bundled into a single PASS/FAIL row. | Create subcases such as UAT-01a registration, UAT-01b verification, UAT-01c invalid login. Record evidence and outcomes per subcase; do not mark the parent PASS if a required subcase failed or was blocked. |
| Evaluation questions assume every respondent used every role's functions. | Use the approved role-specific items or an agreed N/A treatment. A Spotter should not rate admin approval they did not perform. Report actual respondent counts per item/dimension. |
| RTM identifiers are placeholders. | Replace them with approved SRS IDs, keep a requirement-to-subcase mapping, and record scope decisions. The checklist's mention of an RTM does not establish that the IDs match the paper. |

## 3. Suggested acceptance wording

> CEBSPOT is accepted when all mandatory core-workflow subcases pass on the recorded evaluated build; no applicable core subcases remain blocked or untested; no unresolved Critical issues remain; and no unresolved High issues affect core task completion, authorization, privacy, booking consistency, or payment integrity. Any allowed exception is documented and explicitly approved. Only agreed minor issues may remain for “Accepted with Minor Issues.” Questionnaire results are reported separately using the approved study's evaluation criteria.

Define any overall pass-rate threshold before execution. Record both **unique cases** and **tester executions**: 20 parent scenarios performed by multiple people are not simply 20 execution results. Report N/A separately and explain the denominator. For final summaries, use each execution's latest applicable result rather than adding Cycle 1 and retest results together.

For each questionnaire item, calculate `sum(rating × response count) / valid response count`. Do not average role means equally when role sizes differ unless the approved method explicitly requires that weighting. State how dimension means, grand mean, missing/N/A responses, and rounding are handled. Specify the ISO/IEC 25010 edition and the exact approved questionnaire; the selected dimensions do not by themselves establish complete standards coverage or measured technical security.

## 4. Execution records and preparation

Add to execution records: subcase ID, requirement ID, build, account/fixture reference, prerequisite state, expected status/amount, start/end time where relevant, evidence reference, issue ID, and retest build. Add reproduction steps, assignee, fix build, and closure evidence to the issue log. Define who can approve scope exceptions and final acceptance.

Prepare two Spotter accounts for concurrency, two independent owner accounts assigned to different venues for isolation, admin credentials, unclaimed/already-claimed venues, separate owner requests, pending/rejected/approved submissions, free and paid booking fixtures, and reported/valid reviews. One human owner can exercise both owner accounts; accounts are not participant counts. Use controlled payment test data and record whether the provider is in test or live mode. The two-device minimum does not cover a simultaneous three-role workflow; either provide three devices/sessions or document sequential execution.

Freeze which Circle, Activity, and notification functions are mandatory before testing. Remove “where implemented” as a blanket exemption for approved requirements. Assess English/Filipino support explicitly if both are in scope. Retain the ten-day schedule as a plan, but permit additional fixing/retest time if exit criteria are not met on Day 10.

No production data was changed, no app code was changed, and no PASS/FAIL results were entered during this review. Physical-device UAT, deployed-backend verification, and signed participant acceptance remain to be performed.
