# LA-10 staging verification and rollback

Apply timestamped migrations in lexical order through `20261013000500_request_bound_private_uploads.sql` to isolated staging only, after reviewing existing migration alignment as described in `supabase/MIGRATIONS.md`. No existing-database reset is authorized. Deploy `private-upload` with JWT verification, and `private-upload-maintenance` with its own server credential (`verify_jwt=false` is intentional for that scheduler credential).

Set a private `PRIVATE_UPLOAD_WORKER_TOKEN` of at least 32 characters. Schedule an hourly server POST to `private-upload-maintenance`, with that Bearer credential. It removes at most 50 unlinked objects older than 24 hours through the Storage API; repeat successful runs until no backlog remains. A 503 requires retry. Never delete only `storage.objects` metadata, which would leave blobs behind.

Owner applicants sign in with their personal account, supply a separate unregistered business email, and create a server-owned 30-minute draft. Upload 1–3 synthetic JPEG/PNG/PDF documents, at most 5 MiB each, before protected submission. Server upload admission allows 10 uploads/user/hour and at most 5 per request; retrying a consumed request may require a new draft after expiry. No direct client document write/delete or anonymous application insertion is allowed. Failed partial uploads are cleaned by the scheduler after 24 hours. Linked legacy documents remain private and reviewable by an administrator.

Run actual Auth/Storage API probes for anonymous, applicant A, applicant B, assigned venue owner, unrelated owner and administrator. Applicant A can read only their scoped draft documents; reviewing admin reads only linked application documents. Other owners have no application-document access. All direct inserts/updates/deletes must remain denied even with a permissive legacy policy. Repeat protected submissions and simultaneous same-email applications; only one pending application may survive. Confirm predictable upload 429 and `Retry-After`, not a successful upload message.

Deploy an isolated face service using `face-blur-service/README.md`: same staging Auth project, HTTPS, exactly one worker and one replica, no autoscaling. Upload, poll and download with the customer's access token; foreign or anonymous requests must fail. Saturate the queue with synthetic images and verify 429, single processing concurrency, 60-second worker termination, upload timeout, TTL cleanup, crash/restart cleanup, and bounded disk/memory on the actual Render plan. The local real-detector smoke test uses a generated blank image; human/group-face blur quality and Android interruption/retry still need device verification. Do not test anonymous image processing against production.

Rollback: stop admission and scheduled workers, retain private buckets and RLS restrictions, and keep proof/owner submission RPCs protected. A compatible prior client may be restored only if it uses authenticated endpoints. Do not restore anonymous legacy upload routes or public buckets. Restore application behavior with forward migrations after reviewing linked documents and active holds; never drop ledger or application rows to roll back.
