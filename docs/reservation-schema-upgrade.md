## Focused migration

`supabase/migrations/20261101192553_align_reservation_backend.sql` is generated by
`scripts/build-reservation-upgrade.cjs` from seven unchanged historical migrations.
`tests/remediation/evidence/reservation-upgrade-sources.json` records their hashes.
Run `node scripts/build-reservation-upgrade.cjs --check` to verify provenance.

The migration adds the booking availability, walk-in/table-state, verified
inventory, bounded hold, durable payment, authoritative booking detail, and
reservation-event privacy contracts together. It preserves the installed
`require_active_account()` and `guard_profile_identity()` implementations. A
reservation-specific guard adds confirmed-account and deletion checks without
replacing those shared guards. Direct client reservation updates/deletes remain
blocked; authorized server RPCs are the write boundary.

Reviewed adaptations from the original SQL:

- Idempotent tables, columns, indexes, policies, triggers and Realtime membership.
- No global reservability change, no legacy hold/payment business-row backfill.
- Existing attempts receive `reconciliation_required` only when adding their new
  state column; new attempts default to `active`. Existing amounts, statuses,
  provider references and original columns remain intact.
- Existing cancellations/attendance implementations are retained as internal
  functions when installing wrappers; rerunning does not rename a wrapper again.
- An installed reservation-details validator is retained exactly, including the
  later service-only account-erasure exception. It is created only if absent.
- The legacy admin activity policy is restricted to authenticated callers so an
  anonymous activity read cannot execute an authenticated-only helper.
- Payment-proof Storage remains private, restricted to related accounts, with
  validated server uploads. No public-upload fallback is introduced.
- Explicit service-role grants, private-table PUBLIC revocations, and a PostgREST
  schema-cache reload. Existing foundation migrations are never replayed.

Preflight rejects missing identity prerequisites or duplicate provider payment
references. All changes run in one transaction, with a 5-second lock timeout and
60-second statement timeout. An error rolls the transaction back.

## Deployment limits and rollback

This migration does not deploy Edge functions, publish Android updates, change
payment provider mode/secrets, install the owner-application/private-upload schema,
or run real payments. Confirm deployed checkout/webhook/maintenance and private
upload dependencies before claiming paid booking is working. Never invoke a
payment or upload endpoint merely as a health check.

Existing unverified inventory stays unverified. The owner must check physical
tables/capacities and the intended fee (the preflight reported PHP 1). Do not
enable bookings by forging the verification timestamp.

If SQL fails, inspect the sanitized error, confirm rollback, correct and retest
locally before retrying. If a post-deployment issue appears, keep booking unavailable
while preparing a forward correction. Do not drop new tables/columns, revert to
permissive policies, erase new payment events, or restore an entire backup over
newer customer writes. Recovery from the encrypted snapshot requires a reviewed
targeted restore with conflict checking; it has not been rehearsed as full-project
recovery. Inventory/price changes are owner business decisions, not rollback tools.
